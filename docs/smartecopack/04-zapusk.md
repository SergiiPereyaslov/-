## 2. Ключові технічні рішення

1. **Два дерева маршрутів замість `[locale]` + rewrite.**
   Стандартний підхід із rewrite у proxy (Next 16 перейменував middleware.ts
   на proxy.ts) ламає клієнтську навігацію
   App Router: RSC-запити до переписаного шляху повертають 404. Виявлено
   браузерним тестом, гіпотезу про `trailingSlash` перевірено й відхилено.
   Тепер `src/app/(uk)` у корені та `src/app/(ru)/ru` над спільними
   реалізаціями в `src/views/`.

2. **301 у `proxy.ts`, а не в `next.config`.**
   При `trailingSlash: true` вбудований `redirects()` спрацьовує вже після
   нормалізації слеша й дає ланцюжок 308 → 301. Тому нормалізацію вимкнено
   (`skipTrailingSlashRedirect`) і слеш додає proxy — після перевірки
   legacy-мапи. Старий URL веде на новий **за один хоп**.

3. **Кошик поза React** (`useSyncExternalStore` + localStorage) — стан живе
   в браузерному сховищі, читати його ефектом означало б зайвий каскадний
   рендер і розсинхрон із SSR.

4. **Пошук через `/api/search/`**, а не імпортом каталогу в клієнт: інакше
   кожна сторінка тягнула б увесь `products.json` у бандл.

5. **Обидві ціни видно без реєстрації.** Роздрібна й усі оптові щаблі — прямо
   в картці товару. Це головна відмінність від конкурентів, які ховають опт
   за «зателефонуйте».

6. **Сумісність стакан ↔ кришка** зашита в дані за діаметром вінця
   (110–175 → 70 мм, 250 → 75, 340 → 80, 400–500 → 90). Знімає найчастішу
   помилку замовлення й працює як крос-продаж.

**Що знайшли й полагодили під час QA** — найцінніша частина цього етапу:

1. `/api/search` повертав порожній результат: `force-static` не передає
   `searchParams`. Пошук не працював узагалі.
2. `POST /api/lead` ішов через 308-редирект — тіло запиту могло губитись.
3. Клієнтська навігація не працювала: rewrite у proxy/middleware ламає RSC-запити
   App Router. Знайдено тільки браузерним тестом — curl показував 200.
4. Старі URL вели ланцюжком 308 → 301 замість одного хопу.
5. `NextURL` підганяв слеш цілі редиректу під вхідний запит, через що
   `/catalog/stakany-paperovi` редиректив сам на себе.
6. Мобільна шторка фільтрів не закривалась по Esc і не тримала фокус.
7. Кошик і тема читали `localStorage` в ефекті — зайвий каскадний рендер.
8. `proxy.ts` у корені проєкту Next **мовчки ігнорує**: після перейменування
   з `middleware.ts` (вимога Next 16) усі 301 перестали працювати, а збірка
   пройшла без жодного попередження. Файл має лежати в `src/`.
9. Сторінка 404 під `/ru/` показувалась українською, а перемикач мови на ній
   вів на неіснуючий `/ru/_not-found/`. Локаль тепер передається із proxy
   заголовком, який читає `global-not-found.tsx`.
10. Два екземпляри пошуку в шапці (десктопний і мобільний) мали однаковий
    `id` — ламалась прив'язка `<label>` до поля.

Кожен із цих десяти дефектів проходив повз `curl`, типізацію й лінт.
Знайшов їх лише прогін у справжньому браузері.

11. Пошук не знаходив «Стакан» з великої літери: `ILIKE` в PostgreSQL
    залежить від `LC_CTYPE` кластера, і при локалі `C` кирилиця не
    згортається взагалі. Тепер пошук іде по нормалізованому полю, яке
    будує застосунок, — цілий клас мовчазних поломок на чужому сервері
    прибрано.
12. У половини сторінок назва компанії дублювалась у заголовку:
    «Каталог … — SmartEcoPack | SmartEcoPack», бо шаблон кореневого
    layout додається після обрізки title.
13. `proxy` додавав завершальний слеш до `/icon` і `/og` — браузер
    отримував 301 замість картинки.
14. Картинка для соцмереж була відсутня на всіх сторінках, крім кореня:
    файлова конвенція `opengraph-image` чіпляється лише до кореня своєї
    групи маршрутів, а їх у проєкті дві.

### Постійні e2e-тести

Щоб знайдене не повернулось, перевірки зафіксовані як тести (`web/e2e/`,
Playwright, проти продакшн-збірки, desktop + mobile):

```bash
cd web && npm run test:e2e
```

58 тестів: клієнтська навігація без перезавантажень, фільтри, пошук,
наскрізне оформлення заявки, збереження кошика, калькулятор брендування,
мапа 301, sitemap, мета-теги й ліміт title, дублювання бренду, картинки
для соцмереж, RSS, гео-сторінки, 404 обома мовами, доступність шторки,
клавіатурна навігація, вхід в адмінку та поширення правки ціни на сайт,
секторні посадкові (canonical, обсяг тексту, посилання в каталог),
відсутність секторів у шапці й перемикання варіантів A/B.

Запуск у пісочниці, де Playwright не має власного Chromium:

```bash
PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium npm run test:e2e
```

### Продуктивність: чесна цифра

У дизайн-системі я заклав бюджет **< 120 KB JS gzip**. Фактично вийшло
**~180 KB**. Це майже повністю базовий рантайм React 19 + Next 16; власний
код сторінки — одиниці кілобайтів. Бюджет був нереалістичний для React-
застосунку, і я його не виконав. Що з цим робити:

- **Прийняти.** Сторінки віддаються статичним HTML, тому LCP від JS не
  залежить — контент видно до гідратації. Для B2B-каталогу це прийнятно.
- **Або скоротити** — прибрати інтерактивність із картки товару в сітці
  (степер і «в кошик» лишити тільки на сторінці товару). Це зменшить
  клієнтський код, але підніме кількість кліків до замовлення. Не рекомендую.

Реальні Core Web Vitals треба міряти після запуску на бойовому хостингу —
локальні цифри не показові.

## 4. Чек-лист запуску

### Блокери — без цього запускати не можна

- [ ] **Повний краул старого сайту** (Screaming Frog → Export → Internal:HTML).
      Потрібен для мапи 301: зараз бракує URL товарів і слагів статей.

- [ ] **Реальне вивантаження товарів** замість демо-каталогу. Імпорт уже
      готовий: `npm run catalog:import -- файл.csv` або сторінка «Імпорт»
      в адмінці.
- [ ] **Токен Telegram-бота й ID чату** (`TELEGRAM_BOT_TOKEN`,
      `TELEGRAM_CHAT_ID`) або доступ до SMTP. Код готовий; без них заявка
      збережеться в БД, але менеджер не отримає сповіщення.
- [ ] **Юридична вичитка** `src/data/legal.ts`. Це чернетки за типовою
      практикою, не юридичний висновок.
- [ ] `NEXT_PUBLIC_SITE_URL` = бойовий домен; `DATABASE_URL` бойової бази.
- [ ] Кластер PostgreSQL із UTF-8-локаллю (`--locale=C.UTF-8`), не `C`.
- [ ] Прогнати `npm run test:e2e` на бойовій збірці після імпорту даних.
- [ ] Перший `docker compose build` на **тестовому** сервері: образ у
      середовищі розробки не збирався, демон Docker був недоступний.

## 5. Що свідомо не робилось

| Що | Чому |
|---|---|
| Онлайн-оплата | За рішенням: каталог + кошик-заявка, менеджер виставляє рахунок |
| Особистий кабінет клієнта | Немає в узгодженому обсязі; історія замовлень доступна менеджеру в адмінці |
